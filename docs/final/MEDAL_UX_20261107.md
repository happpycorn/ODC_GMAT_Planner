# 金牌賽 UX 重新設計（11-07）

目標：一個人在 GUI 上，每回合 10 分鐘內穩定交出正確的提交行。CLI 是備援，流程跟 GUI 一一對應。
依據：規則第 3、6、7 節（`rules/四強賽規則_20261029.pdf`）、11-07 彩排（`docs/final/mock_drill_20261108/`）的六個問題。

## 1. 主辦給的東西 → 我們怎麼接

| 時刻 | 主辦給什麼（推測） | 我們存成 | 從哪裡進 |
|---|---|---|---|
| 開賽公告 | 五項參數（ΔV_lim、R_cap、T_round、安全空域、雙方 r0／v0＋epoch），多半是投影片 | `day/announced.json`（規則）、`day/initial.json`（狀態）、`day/announce_input.json`（原始輸入＋單位，留底） | GUI「抄公告」一頁；CLI 改範本 |
| 開賽公告（可能有） | USB 初始狀態檔 | `day/<原檔名>` | 拖進「抄公告」頁，自動跟手打值比對 |
| 每回合結束 | USB 狀態檔（雙方 r、v，可能有 epoch；Δv 被縮放才列） | `day/<原檔名>`（不改名） | GUI 回合頁拖檔；CLI `announce --state` |
| 每回合結束（可能有） | 口頭／投影片公告雙方實際 Δv | session 內 | GUI 回合頁選填；CLI `--opponent-dv` 選填 |

狀態檔是唯一必要的輸入；Δv 一律從狀態檔反推，手打的 Δv 只拿來交叉比對。

## 2. 開賽：抄公告（10 分鐘）

### 2.1 時間表

| 時間 | 做什麼 | GUI |
|---|---|---|
| 0–3 分 | 照投影片抄五項 | 「抄公告」頁一張表，按「存檔」 |
| 3 分 | 角色選擇器自動開跑（預設完整版 150 s，可勾快速版） | 存檔成功後自動開始，不用換頁 |
| 3–6 分 | 等結果；有 USB 檔就拖進來比對 | 同一頁下方顯示比對結果 |
| 6–9 分 | 看選擇器建議、依手冊三條規則決定 | 結果卡片直接寫「建議：躲方」＋三條規則各自打勾 |
| 9–10 分 | 告知工作人員、建 session | 按「我們選躲方」或「我們選追方」一顆鈕就建好 |

### 2.2 「抄公告」表單

排版照規則第 7 節的順序，每個欄位旁邊有單位下拉，存檔時換成工具的單位：

| 欄位 | 可選單位 | 存成 |
|---|---|---|
| ΔV_lim（雙方相同，一格） | m/s、km/s | `max_dv_pursuer_mps`＝`max_dv_evader_mps`（m/s） |
| R_cap | km、m | `capture_radius_km` |
| T_round | 秒、分鐘、小時 | `window_sec` |
| 安全空域下限、上限 | 半長軸 km、高度 km（＋6378.137）、高度 m | `safe_sma_km` |
| 追方船名、逃方船名（選填） | — | session 的船名對應（見第 4 節） |
| 雙方 epoch | 文字：`09 Nov 2026 05:30:00.000`、ISO、GMAT ModJulian 數字都吃 | `initial.json` 的 `epoch` |
| 雙方 X、Y、Z | km、m | `r_km` |
| 雙方 VX、VY、VZ | km/s、m/s | `v_kms` |

位置、速度一列六格，旁邊有「貼上一整列」小框：貼 `6581.05 867.10 1748.22 0.1826 6.5320 -3.9137` 這種空白或逗號分隔的六個數，自動分到六格（投影片如果能拿到電子檔就省很多時間）。

存檔前即時檢查，有問題的格子變紅並寫原因，不擋存檔（主辦的題可能真的很怪），但要按「我確定」：
- |r| 不在 6,500–50,000 km、|v| 不在 1–11 km/s →「看起來單位不對：位置是公尺嗎？」
- 近地點高度 < 0 →「這條軌道會撞地，多半是某個數字打錯（常見：正負號、小數點）」
- 兩艘 epoch 差 > 1 天 →「兩艘 epoch 差 N 小時，確定嗎？」；差 > 0 時顯示「較早那艘會先用二體推 N 秒對齊」
- 安全空域 lo ≥ hi、或高度換算後 < 6378 → 擋存檔
- ΔV_lim > 1000 m/s →「是不是單位選錯（km/s）？」

存檔後下方印「念回」卡：大字逐欄列出換算後的值、每艘的高度／近地點高度／半長軸／週期，旁邊並排原始輸入值，給自己對照投影片看一次（取代「驗證唸數字」）。

### 2.3 有 USB 初始狀態檔時

拖進同一頁就解析（套用表單裡填的船名），跟手打值逐格比對：
位置差 < 1 m、速度差 < 1 mm/s、epoch 差 < 1 s 算一致；不一致的格子標紅並列出兩邊的值。
按「以 USB 檔為準」會把 USB 值覆蓋進 `initial.json`（規則說下一回合起點以電子檔為準，初始狀態沒講，所以預設不自動覆蓋，讓你選）。

### 2.4 CLI 備援

- 規則：照舊 `cp configs/rulesets/final_official.json day/announced.json` 改四個數字。
- 初始狀態：新的 `configs/initial_template.json`，`cp` 到 `day/initial.json` 改 epoch、r、v 共 14 格。
- `copilot.py final parse day/initial.json` 印念回摘要（現有功能，已驗證吃這種 JSON）。
- 手冊步驟 1、2 合併成「抄公告」，`final manual` 降為「範本也壞了才用」。

## 3. 每回合（10 分鐘 × 6）

### 3.1 一條路

GUI 回合頁只有一個主按鈕位置，依狀態變成下一個動作，不再有「選狀態檔」「記錄公告」兩組下拉：

```
[第 N 回合] 倒數 09:12
① 放入第 N−1 回合結束的狀態檔（第 1 回合沒有這步）
   → 自動：解析（用 session 記住的船名）→ 反推雙方 Δv → 核對 → 寫進 session
② 自動取得建議（不用按；失敗才出現「重試」「快速版」）
③ 大字提交行＋逐軸正負號 → 手寫 → 在「照紙上打一次」框打回來 → 綠燈
④ 按「已交出」→ 記下交出時刻，畫面切到「等主辦公告」
```

正常回合的操作：拖一個檔、抄一行、打一行、按一顆鈕，共 4 個動作。

### 3.2 每一步會出什麼錯、怎麼擋

| 步驟 | 可能的錯 | 怎麼擋 | 畫面上的話（例） |
|---|---|---|---|
| ① | 放錯檔（本回合起點、上一回合的舊檔） | session 記每份已用過的檔（內容雜湊＋epoch）；同一份再放 → 擋；epoch 等於本回合起點 → 擋 | 「這份檔第 3 回合已經用過了。請放主辦剛發的檔（應該是 07:45 的狀態）。」 |
| ① | 船名認不出 | session 記住 `new` 時的船名／順序（第 4 節）；還是認不出就跳出兩個下拉讓你點選「哪個是追方」 | 「檔裡的船叫 SC_Red、SC_Blue，請點哪一艘是追方。之後每回合會記住。」 |
| ① | 單位錯（m、m/s） | 沿用現有的單位提示 | 「逃方位置看起來是公尺，請確認檔案。」 |
| ① | 回合中途攔截／撞地，檔是結束時刻的狀態 | 用 epoch 差算經過時間；反推後二體推演本回合軌跡，判斷是否 ≤ R_cap 或撞地 | 「依這份檔，本回合 07:52:10 距離 6.1 km ≤ R_cap，比賽應該已結束（追方勝）。以主辦公告為準。」 |
| ① | epoch 差 ≠ T_round | 用 epoch 差反推；差 > 1 s 就警告 | 「檔案時間比回合起點晚 840 s，但 T_round 是 900 s：T_round 抄錯，或主辦中途結束？」 |
| ① | 反推的 Δv 超過 ΔV_lim | 不可能發生 → 檔或規則有錯 | 「反推對手 Δv = 412 m/s，超過上限 200：檔案或 ΔV_lim 有錯，先核對公告。」 |
| ① | 我方反推 Δv ≠ 提交行 | 差 > 0.05 m/s 警告 | 「主辦執行的我方 Δv 跟你交的差 3.2 m/s（Y 軸）：主辦抄錯或我們手寫錯，現在去問工作人員。」 |
| ① | 手打的對手 Δv（選填）≠ 反推值 | 差 > 0.05 m/s 警告；以檔案為準 | 「你打的對手 Δv 跟檔案反推差 5.0 m/s。檔案反推值 [..] 是主辦實際執行的，已採用。」 |
| ② | advise 太慢 | 6 分鐘還沒出來就自動改跑快速版 | 「建議太慢，已改用快速版。」 |
| ② | 重驗未通過 | 大字提交行直接換成工具給的替代值 | 「重驗沒過，已換成替代值，抄這行。」 |
| ③ | 抄錯正負號、位數 | 「照紙上打一次」框逐字比對，不同的字元標紅 | 「Y 軸你寫 46.44，應為 −46.44。」 |
| ④ | 超時 | 倒數 7:00 黃、8:30 轉紅；9:00 還沒按「已交出」就跳大字「現在就交」 | — |

### 3.3 倒數

- 第 1 回合：建好 session 後按「第 1 回合開始」。第 2 回合起：放入狀態檔時自動開始（假設檔一發下來就開始算 10 分鐘），旁邊有「−1 分」「−2 分」鈕補拿檔的延遲，也可以手動重設。
- 段落：0–1 分放檔、1–4 分建議、4–7 分抄寫核對、7–8 分交出；8:30 轉紅、9:00 跳「現在就交」。
- 頁首一直顯示：回合數、倒數、我方角色、目前距離、逃方 a 是否在安全空域。

### 3.4 CLI 備援

```bash
.venv/bin/python copilot.py final advise day/session.json                         # 每回合只這兩行
.venv/bin/python copilot.py final announce day/session.json --state day/<回合末檔>   # 加 --opponent-dv X Y Z 可交叉比對
```

`advise` 不再需要 `--state`（announce 已經把狀態寫進 session）；舊用法 `advise --state` 保留給換電腦重建狀態時用。
沒有狀態檔、只有口頭 Δv 時用舊的 `announce --opponent-dv X Y Z`。

## 5. 從狀態檔反推 Δv（問題 4、5）

### 5.1 算法

已知本回合起點（session 的 `current_state`，含 epoch）與回合末（檔案）的雙方 r、v：

1. 經過時間 dt：兩份都有 epoch 用 epoch 差（每艘各自算）；任一份沒有就用 T_round。
2. **主算法：把回合末狀態往回推 dt**（二體，`propagate(-dt)`），得到推力後的 r0′、v0⁺。Δv = v0⁺ − v0。
   回推的 r0′ 跟起點 r0 的差就是檔案品質檢查（正常 < 1 m）。
3. **交叉核對：Lambert（r0 → r1，dt）**，取 0 圈、順行解，比較兩法 Δv 差（正常 < 1e-3 m/s）。

建議用回推當主算法、Lambert 當核對（你原本寫 Lambert）：回推用到檔案的完整 r、v，沒有長短路徑和多圈的分支問題，而且「回推位置不回到 r0」本身就是很強的放錯檔訊號。T_round ≥ 半個週期時 Lambert 的分支要另外選，回推不受影響。兩法差 > 0.01 m/s 時以回推為準並警告。

精度：彩排 CSV 是 km 6 位、km/s 9 位小數，反推誤差約 1e-6 m/s；即使主辦只給 km 3 位、km/s 6 位，誤差約 1e-3 m/s，遠小於 0.05 m/s 門檻。我們 μ = 398600.4418、GMAT 預設 398600.4415，影響 < 1e-6 m/s。

### 5.2 `announce` 新行為

```
announce SESSION [--state 檔] [--opponent-dv X Y Z] [--our-dv X Y Z] [--names ..] [--order ..]
```
- 至少要有 `--state` 或 `--opponent-dv` 其中一個。
- 有 `--state`：反推雙方 Δv → 寫 `rec["announcement"]`（`source: "state"`，含反推值、回推殘差、Lambert 差）；有手打值就比對（0.05 m/s）。
  session 的 `current_state` 換成檔案狀態、回合 +1。對手偏好分類用反推值。
- 只有 `--opponent-dv`：舊行為（二體預測下一回合起點）。
- 印出：雙方實際 Δv（被縮放的標「已縮放到 ΔV_lim」）、本回合最近距離與時刻、逃方 a、是否應已結束。
- 第 6 回合 announce：印最終 a 是否在安全空域、勝負推斷。

### 5.3 邊界情況

| 情況 | 處理 |
|---|---|
| 對手被縮放 | 反推值本來就是實際執行值，不需特別處理；|Δv| 在 ΔV_lim ± 0.01 時標「疑似被縮放」 |
| 逾時當 [0,0,0] | 反推 ≈ 0，照常記錄；我方反推 ≈ 0 而提交行不是 0 → 「主辦當我們逾時？」 |
| 回合中途攔截／撞地 | 依二體推演本回合軌跡，印出應已結束；session 標 `finished`，回合頁顯示結束畫面 |
| 檔案只有一艘 epoch | 照現有規則報錯 |
| 第 1 回合兩艘 epoch 不同 | 起點已在 `new` 時對齊到較晚的 epoch；回合末檔的 epoch 對這個起點算 dt |
| 檔案沒 epoch | 用 T_round；回推殘差 > 5 km 時提示「時間可能不是 T_round」 |
