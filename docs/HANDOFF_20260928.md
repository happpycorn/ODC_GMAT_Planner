## 任務 2：提早停止（已於 2026-09-29 修好、完成消融，預設關閉）

**結果**：使用者同意選項 (a)，新增 `optimization.EARLY_STOP_ENABLED`，預設 `false`，開啟時把 termination
傳給 mealpy `solve()`。快情境 40/40、窄窗 3/3 全部成功且沒有冷編譯；早停省 CPU 但會掉分，
`contest_fastT` 最差 −1.7269、`weird_test` 三顆種子各 −1.9547。預設維持關閉。
完整數據見 [EARLY_STOP_ABLATION_20260929.md](EARLY_STOP_ABLATION_20260929.md)。以下保留原始診斷與選項供追溯。

**根因**（09-28 讀 mealpy 3.x 原始碼確認）：
- `src/optimizer.py:1522-1523`：`term_dict = {"max_early_stop": self.mes, "epsilon": self.tol}`，傳給
  `L_SHADE(epoch=..., pop_size=..., termination=term_dict)` **建構子**。mealpy `Optimizer.__init__` 用
  `__set_keyword_arguments` 把它設成 `self.termination` 屬性。
- 但 `solve()`（`.venv/.../mealpy/optimizer.py:233`）一開頭呼叫 `check_termination("start", termination, None)`，
  第 191 行 `self.termination = termination` **用 solve 的參數（我們沒傳 = None）蓋掉**。
- 所以所有歷來的 run 都跑滿 MAXITER；budget_v1 198 次「提早停止從未觸發」就是這個原因。
  `_optimize_burn_case` 裡 `note += "，提早停止"` 那段也從沒執行過。

**影響**：歷來結果與 runtime 上界（`docs/prelim/CONTEST_DAY.md` §4.1）都是「跑滿」下量的，本身沒錯；只是 config 的
`MAX_EARLY_STOP`/`TOL` 是死設定，validator/文件都把它當有效參數在講。

**選項**（這是行為改變，要先問使用者）：
- (a) **修好**：改成 `model.solve(..., termination=term_dict)`（兩個呼叫點：`optimizer.py` ~1546 單執行緒、~1548 thread
  模式）。會提早收工 → 省時間，但可能漏掉晚出現的盆地（weird_test 這類窄窗風險最大）。修了必須用 `sweep_params.py`
  做一輪消融（early stop 開/關 × budget_v1 的 4 快情境，最好加 weird_test 3 SEED），比拆後分數最差值與 CPU 秒，
  不退步才開。注意 mealpy 的判定是 `history.get_global_repeated_times(epsilon)`：global best fitness（= −score）
  連續幾代變化 ≤ epsilon 的次數 ≥ max_early_stop 就停；TOL 是分數單位。
- (b) **拿掉**：刪 `MAX_EARLY_STOP`/`TOL` 設定、驗證與文件，明說「永遠跑滿 MAXITER」。
- (c) 先不動，只在 STATUS／config 註解標明是死設定。

**我的建議**：(a)，但先讓預設行為不變（例如修好後預設不傳 termination，或新增開關預設關），跑完消融再決定要不要預設開。
理由：budget_v1 顯示 600 代在多數情境是夠的，提早停止若能在 contest 這類「早就收斂」的情境省時間，比賽當天有用；
但沒數據前不該改預設。
