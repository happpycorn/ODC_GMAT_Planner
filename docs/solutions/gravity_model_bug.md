# 🔴 重大發現：重力模型不一致（2026-09-05，正式比賽當天）

## 問題

- **官方下載的題目 script**（`ODC_2026_prelim_prob.script`，`DefaultProp_ForceModel`）：
  `GravityField.Earth.Degree = 0`，`Order = 0` → **純點質量，沒有 J2/J3/J4 攝動**
- **我們 `configs/contest.json` 原本的設定**：`strategy.GRAVITY_DEGREE = 4`（J2+J3+J4）
- 兩邊不一致，而且**不是小誤差**：用完全相同、完整精度的 Δv 燃燒向量，
  分別在兩種模型下重播同一條軌跡：

  | 模型 | Δr（命中距離）|
  |---|---|
  | J2+J3+J4（我們原本算的）| 0.703 m（幾乎正中）|
  | **點質量（官方真正的環境）** | **136,137 m（136 公里，完全沒打到）** |

  代表這條 Lambert 轉移軌跡對「用哪個物理模型求解」極度敏感，換模型不是「差一點」，
  是**完全不同的答案**。今天稍早找到的 86.28、88.30 兩組「已驗證」解都是在錯誤模型
  （J2+J3+J4）下算的，**已經確認不能用**。

## 已採取的修正

- `configs/contest.json` 的 `strategy.GRAVITY_DEGREE` 已改成 `0`，比賽當天**必須維持這個值**，
  不要因為別的題目/練習題習慣用 4 就手滑改回去。
- 正式搜尋、GMAT 驗證都要在這個設定下重跑（进行中，見 `outputs/best_*` 系列資料夾的時間戳）。

## 教訓（給以後遇到類似狀況）

1. **拿到官方題目 script，第一件事檢查 `DefaultProp_ForceModel` 的
   `GravityField.Earth.Degree/Order`**，不要預設官方一定用跟我們工具一樣的物理模型。
2. **瞄準到公尺等級的 Lambert 解，換一個看似「更粗糙」的物理模型（點質量）不代表誤差變大
   就一定還在合理範圍內**——這題示範了換模型可以讓誤差從公尺級跳到百公里級，
   因為轉移軌跡的初始速度方向對最終命中點極度敏感（shooting problem 的病態性）。
   **任何「驗證過」的解，都要用最終真正會拿去評分的那個物理模型重新驗證過，
   不能只在自己求解用的模型裡驗證就當作數。**
3. 這也代表：如果之後要把 burn table 填進官方原始 script（而不是提交我們自己
   `ShipA/ShipB` 版本），只要**保留官方 script 原本的 `DefaultProp_ForceModel` 不要動**，
   我們產生的燃燒值只要是在 `GRAVITY_DEGREE=0` 下求解出來的，就會跟官方環境一致。

## 🔴 追加發現（同一天，另一個獨立問題）：「~90分」的單棒目標點其實會撞地球

在追查上面的重力模型問題之後，原本給「拆棒」方向的目標點
（T_team≈3,567~3,585s、Δv≈1,578~1,674 m/s，Score≈89.996，不管合不合法的單棒全域最佳解）
**經過逐段掃描驗證，全部撞地球**——最低點落在地表以下 1,882~2,839 km，不是「差一點沒過
5km」的邊際問題，是整條 Lambert 轉移路徑的近地點深深切進地球內部。這整個 T≈3,350~3,900s
的快速時間窗附近，Top 15 高分候選**全部撞地球**，一個能用的都沒有。

真正安全（不撞地球）的單棒解，最高分只有 **84.80**（Δv=7,253m/s，超標，T=5,963.6s），
比已確認的 88.32（2棒）還差。**結論：拆棒方向本身就建立在無效目標上，不用再投入資源。**

**教訓**：找「不管合法與否的最優解」時，只用簡化 Lambert 模型算 Δv/時間，
**沒有同時檢查整條路徑會不會撞地球**——這是這次踩到的第二個坑。以後做這種
「暫時放寬某個限制去找理論上限」的探索，撞地球檢查（逐段掃描最低高度，不能只看
起點/終點）要跟 Δv/時間分數同時做，不能事後才補。
