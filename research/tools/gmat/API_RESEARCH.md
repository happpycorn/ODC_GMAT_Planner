# GMAT 有什麼是我們手刻、但它免費做得更好的？

**結論先講**：GMAT 從 R2020a 起附帶完整的 **Python API**（`gmatpy`），我們手刻的東西
它幾乎都有。但**速度差 35 倍**，所以能不能取代完全取決於「那段程式一次跑幾次」。

## 實測數據（2026-08-29 01:30）

同一組初始狀態、同一個力學模型（JGM2 degree 4 / order 0）、傳播 3,158.3 秒：

| | 位置 | 單次耗時 |
|---|---|---|
| GMAT API（RungeKutta89, Accuracy 1e-11） | 基準 | **7.53 ms** |
| 我們（njit DOP853, rtol 1e-12） | 差 **2.745 m** | **0.214 ms** |

速度比 **35:1**，精度差 2.7 公尺（速度差 0.0038 m/s）。

## 可以取代的（一次跑幾次 = 少）

| 目前的實作 | GMAT 對應 | 一次搜尋跑幾次 | 換過去的成本 | 換過去的好處 |
|---|---|---|---|---|
| `_replay_mission` / `mission_metrics` 的傳播 | `Propagator.Step()` | 約 5 次 x 5 段 | **~0.2 秒** | **回報的分數就是 GMAT 的分數**，Python↔GMAT 落差直接歸零 |
| `refine_lambert_burn`（手刻牛頓法差分修正） | `DifferentialCorrector`（見 `api/Ex_R2025a_BasicTarget.py`） | 同上 | 小 | 用久經考驗的實作取代自己刻的 |
| 六根數↔狀態向量（poliastro） | `Spacecraft.SetField/GetNumber` | 少 | 極小 | 主辦方用的就是 GMAT，等於用權威實作 |
| 驗證階段 spawn `GmatConsole`（每次要開行程 + 解析腳本，約 2~4 秒） | API 常駐在同一個行程 | 1~2 次 | 小 | 快幾秒，而且驗證路徑不再受**非 ASCII 陷阱**影響 |

## 不能取代的

**搜尋階段的傳播器。** 一次完整最佳化約 10 萬次適應度評估，每次含多段傳播。
35 倍代表 76 秒的跑會變成 **44 分鐘以上** —— 90 分鐘的比賽直接出局。
我們的 njit DOP853 必須留著。

**繳交用的 GMAT 腳本。** 規則要交 Script + Report，API 取代不了腳本產生。

## 風險

- API 需要先跑 `BuildApiStartupFile.py` 產生 `bin/api_startup_file.txt`（已在這台做過）。
  比賽當天若換機器要重跑，**多一個會出錯的步驟**。
- 目前的驗證路徑（spawn GmatConsole 跑腳本）跟繳交的東西**是同一份腳本**，
  這個性質很有價值：驗的就是交的。改成 API 驗證會失去這個對應。
  -> **建議：API 用來取代「內部重播」，不要取代「繳交前的腳本驗證」。**

## 建議的優先序

1. **`_replay_mission` 的傳播改用 GMAT API** —— 成本 0.2 秒、消除落差、風險低。
   但要注意這會讓「搜尋代理」跟「重播真值」的差距變大（現在兩邊都是我們的模型）。
   換完必須重跑全套回歸，確認分數變化在預期內。
2. `refine_lambert_burn` 改用 GMAT DC —— 中等價值。
3. 其餘不急。

**全部都要在換完之後跑完整驗證**（六組回歸 + 兩份測試 + 官方範例題目 GMAT 端到端）。
